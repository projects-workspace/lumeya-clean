## 1. Current product

This checkout contains a public, guest-only discovery MVP for holistic and nature-oriented services, practitioners, organisations, places, and events. The broader mapped vision is an international service-centred network; Provider Space, personal workspaces, and other later capabilities remain future product context rather than a completed platform.

## 2. Major capabilities

- **Public discovery — implemented as structured static content.** Discover, Services/categories, Practitioners/providers, Places/map, Events, About, Join Lumeya, and public request pages render from a validated catalogue. Editorial records live in `content-source/published/catalog.json`; `scripts/catalog.js` generates the browser export `discovery-data.js`. Blank entity templates and a publication workflow are documented in `docs/catalog-publishing.md`. The release-gate journey remains `Deep Massage & Tea Ceremony → Ivan Protinyak → Santiago Studio Praha → public request`.
- **Categories and provider records — implemented.** Categories include body and movement, holistic wellbeing, relationships and personal growth, nature-oriented living and craft, and community and creative work. Empty categories remain browsable and invite relevant provider submissions. The provider template and shared directory support both practitioners and organisations; there is no organisation record in the current catalogue.
- **Map — list-first with verified-pin enforcement.** Providers and places remain visible in the filtered list, including records without precise locations. A marker requires coordinates explicitly marked verified with a public source URL; inactive places remain list-only. Current published records contain no verified coordinates, so the Map control is disabled and the list remains available.
- **Guest contact and correction requests — deployed; hosted receipt verified.** Service cards explain whether contact reaches the published provider contact or a Lumeya operator and what the visitor must do next. The core massage request preserves provider/place context; `lila-reading` exposes its supporting supplied profile and matching Telegram contact with explicit verification limits. Services, providers and places link to correction intake carrying the original collection/ID. New forms use the additive M3 keyed RPC candidate; exact retries keep the same UUID, changed content is rejected without writing, and each distinct submission needs a new explicit submit. Online submission requires browser storage to persist the key; uncertain receipts do not offer a second Telegram send. The legacy RPC remains for older callers. A correction never directly edits a listing. Receipt persistence, worker notification and Telegram sending are distinct. Migration 0017 and the current frontend are now in Production. Keyed PostgREST retries and a synthetic browser-to-database receipt passed on 2026-10-01; operator notification delivery remains unverified.
- **Operator editorial loop — implemented and accepted locally.** `scripts/editorial.js` maintains a private filesystem queue outside the repository/web root, imports original remote receipts or received manual envelopes, records clarification/rejection, requires recorded identity/source checks and an explicit approval of the exact review hash, then writes approved public fields through the existing catalogue generator. Corrections preserve IDs and reject intervening edits. Exact intake/publication retries deduplicate; source/export regeneration recovers interrupted publication. Anonymous HTTP users have no queue-read, approval or publication endpoint. This is operator CLI/repository tooling, not Provider Space or a CMS. The loopback preview demonstrates real local disk receipts and is distinct from the later hosted receipt checks and still-unverified worker delivery.
- **Events — bounded public reads with separate states.** Discover and Events acquire the current publishable client at read time, bound the query to upcoming confirmed public stored dates in the next six months (maximum 200), abort after 10 seconds, and offer retry. Empty, unavailable and unconfigured schedules have distinct copy. No future dates are inferred from legacy recurrence rules. An API read returned HTTP 200/empty on 2026-09-30. After the authorized 2026-10-01 release, the live Events page rendered a valid empty upcoming schedule with its undated formats; this does not prove ongoing health or explain the earlier intermittent failures.
- **Legacy platform — retained, not an authenticated product.** Account, calendar, favourites, booking, community, and provider-facing files remain in the repository. The public MVP forces guest identity and clears legacy browser IDs. These older flows are dormant or otherwise outside the public MVP and must not be described as secure authenticated capabilities.

## 3. Technical foundation

The frontend is a multi-page static site written in HTML, CSS, and vanilla JavaScript, with no compile/build step. Structured editorial JSON is validated against a public-field allowlist and rendered to `discovery-data.js`; browser code consumes only that published export. The browser loads Supabase JS for the keyed request RPC candidate and scheduled-event query, Leaflet for mapping, and hosted fonts. Browser identity is deliberately disabled; the site uses a publishable Supabase key only. Pending/failed form drafts and retry keys are local, unencrypted and expire after seven days; online submissions are blocked if the key cannot be persisted. The operator queue is separate local plaintext with directory mode 700/file mode 600, outside the repository and public root. `.vercelignore` excludes `content-source/` and `scripts/` from the static deployment input. The optional loopback editorial preview has no hosted deployment and exposes write-only intake using the same request envelope.

The separate `bot/` Node.js service uses Telegraf and `supabase-js`. It supports the Telegram request fallback, service-role database operations, and a polling worker that claims up to 20 queued public requests, sends them to the configured admin chat and records notified/failed state; migration 0016 caps a request at eight claim attempts. Delivery requires a running worker and its external credentials. The service-role-only 90-day cleanup RPC needs a separately configured schedule/caller. Hosted claim/expiry definitions and grants were verified read-only on 2026-10-01; worker execution and an active cleanup caller remain unverified. Supabase has no pg_cron and the mapped Vercel project has no configured cron jobs. The root `.vercelignore` keeps the static-site deployment boundary separate from the bot and verification tooling. The repository documents a GitHub Actions verification workflow.

## 5. Current limitations and decisions

- Published catalogue content is static and generated from the validated JSON source. The current map has no verified listing coordinates. Nature-oriented/ecological/craft categories are available for future sourced content but have no catalogue service entries today.
- Forms use `submit_idempotent_public_discovery_request`; migration 0017 is applied in the dedicated Production project. Actual PostgREST checks passed for sequential/concurrent retries, generic conflict without overwrite, distinct keys, fingerprint rate limiting, invalid input, legacy compatibility and anonymous read/update/helper denial. A production service → practitioner → place → request browser journey persisted a synthetic receipt. The full legacy chain remains unproven. Hosted notification delivery and scheduled retention execution remain unverified.
- No real provider submission was received or published during M2. Source-backed provider identity/relationship checks and actual editorial decisions remain operator work. Nature/ecological/craft categories still have no real published services; missing content remains a content-growth gap, not a blocker for the accepted bounded MVP. The supplied Violetta profile supports the existing Lila offer/contact, but current identity, availability and qualifications were not independently checked. The public Telegram page could not be fetched; no outreach occurred.
- Local queue/catalog locks refuse concurrent edits. After a killed operator process, confirm no writer is running before manually removing its stale lock and retrying. Local private storage is not encrypted or a hosted authenticated workspace.
- Browser login and the legacy private workflows are not implemented as a secure authenticated experience. Never restore caller-supplied Telegram IDs as identity.
- Automatic request notification and deletion of expired requests are post-MVP operations requiring a verified running worker/caller. The accepted operator path is private receipt export/import and explicit manual review/publication; the 90-day expiry timestamp is not proof of automatic deletion. The public intake has validation, a honeypot, and basic database rate limiting when request headers are available, but no edge-level rate limit or CAPTCHA. Failed-request drafts and retry keys are not encrypted in browser storage.
- `docs/security.md` records migration 0016 and live request/RLS checks as historical evidence from 2026-08-31. Migration 0017 passed local SQL checks and was later applied in Production after the scoped hosted prerequisites were verified compatible on 2026-10-01. The remote migration history and pre-existing legacy schema objects differ; no live reset/replay is permitted or inferred.
- Keep the static discovery MVP and its narrow request path as the current implementation boundary. Stage 1–3 concepts do not automatically expand this scope.
